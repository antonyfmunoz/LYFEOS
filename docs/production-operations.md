# LyfeOS production operations

## Release gate

Before a production release, run `npm run verify`, review `git diff --check`, and confirm the public `/api/ready` endpoint returns `{"status":"ready"}` after deployment. The included GitHub Actions workflow enforces the same build and test gate once it is pushed to the repository's `main` branch or used from a pull request.

## Availability and sessions

Fly checks `/api/ready`, which verifies a live database query. Authentication sessions are stored in Postgres table `session`, so a machine restart does not sign users out. The release migration `0009_postgres_sessions.sql` must be applied before enabling a release that uses the Postgres session store.

## Monitoring and alerts

GitHub Actions runs the `Production monitor` workflow every five minutes against `https://lyfeos.net/api/ready` and the expected anonymous `401` response from `/api/auth/me`. A failed check opens one labelled `production-monitor` incident issue with the failing workflow receipt. The first successful subsequent check comments on and closes that incident. Configure GitHub notification delivery to **Email** and **Only notify for failed workflows** for the `antonyfmunoz/LYFEOS` repository so incident creation and monitor failures reach the operational owner.

The same workflow can check `/api/operations/health-integrity` through a fail-closed server-only token. Generate one random value of at least 32 characters, store it as the Fly secret `LYFEOS_MONITOR_TOKEN`, and store the identical value as the GitHub Actions repository secret `LYFEOS_MONITOR_TOKEN`. Do not put it in client code, workflow output, issue text, or source control. Until both secret locations are configured and a scheduled run succeeds, the workflow emits a warning and health-integrity alerting is **not live**.

The integrity endpoint reports only aggregate counts and normalized status. It never returns user IDs, provider payloads, health values, notes, credentials, cursors, or vendor messages. It returns `503` for critical integrity defects, stale 15-minute sync/execution leases, overdue retry state, abandoned imports, repeated connector failures, or active connections carrying an error. Expected user-controlled deletion outcomes—such as a completed program session retaining a lost-link receipt, or a successful planning handoff whose mission was later deleted—remain informational and do not page the operator. A healthy report returns `200` with `status: "healthy"`; `critical`, `degraded`, and query-unavailable reports return `503` and use the existing incident workflow.

Each integrity snapshot runs inside a read-only transaction with a three-second database statement timeout. Concurrent endpoint requests share one in-flight snapshot instead of multiplying fleet scans. Before production activation, run `npm run ops:health-integrity` against an isolated current-schema staging branch. It performs three sequential read-only snapshots by default, prints only status, incident totals, and timing, and exits nonzero for a degraded/critical report, timeout, or query failure. `HEALTH_INTEGRITY_DRILL_ITERATIONS` may be set from `1` through `20`; keep the default for routine release qualification. This command is a staging query/failure receipt, not production load evidence and not a backup-restore drill.

The application emits structured request logs with `x-request-id`; Fly remains the live source for runtime logs and machine health. Sentry is initialized only when `SENTRY_DSN` is present. Its React initializer runs before the application, captures browser errors, and traces page/API activity; the server captures Express errors, uncaught exceptions, and unhandled rejections. Create a Sentry alert for new issues in the LyfeOS project and route it to the operational owner. The Sentry project is not live until its DSN is stored in Fly and a test event is received. Medium-risk assistant mutations enter a 15-minute user approval queue; expired/declined actions must leave an activity receipt and make no domain change.

## Backup and restore

Neon is the authoritative recovery provider. Its branch history supports point-in-time recovery; retain at least seven days of history (or 30 days on a plan that supports it). Before changing schema or destructive data, create a Neon snapshot and record its timestamp and restore point in the release notes. At least quarterly, create an isolated branch from a snapshot or a point in time and verify: schema, one login, one account creation, and one mission read/write. Delete the temporary branch after the evidence is recorded. Never run a restore against production without an explicit change window and approval.

## Schema rollback policy

LyfeOS database migrations are forward-only, numbered, additive where possible, and idempotent in the release runner. Do not run an improvised down migration in production. Before traffic moves, verify that the prior application release remains compatible with the post-migration schema. If it is compatible, an application-image rollback may use the existing schema; record the image identity and do not mark the database as rolled back. If it is not compatible, keep or freeze the current application and ship a reviewed forward-fix migration. Any destructive correction requires an explicit change window, a fresh provider snapshot/restore point, scoped impact verification, and approval. A managed preview/staging migration and rollback rehearsal is still required before a production release that changes schema.

## Incident response

1. Confirm `/api/health` and `/api/ready`.
2. If the health-integrity monitor fired, inspect its aggregate category and the corresponding sanitized import/connection receipts; do not copy health payloads into an incident issue.
3. Inspect Fly logs using the `x-request-id` returned to the affected user.
4. If a release is the cause, roll back to the last healthy Fly image before modifying data.
5. If data integrity is affected, freeze writes, take a snapshot, and restore only through the provider-approved procedure.

## External operating gates

These controls require separate provider configuration or ownership before claiming mature SaaS operations: Neon backup retention and quarterly recovery evidence, product analytics consent and retention policy, billing/entitlement controls, support intake, and a named operational owner.
